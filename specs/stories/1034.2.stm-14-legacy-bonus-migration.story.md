# Story 1034.2 (STM-14b): One-shot migration of persisted .bonus values into audited st_mods

## Status

Draft

## Story

**As a** storyteller,
**I want** every existing persisted ad-hoc `.bonus` value on live character documents converted into an equivalent audited `st_mod` and the `.bonus` field then zeroed,
**so that** all situational bonuses (historical as well as new) are auditable and there is a single source of truth for ad-hoc adjustments after STM-14.

## Acceptance Criteria

1. Given the live `characters` collection, when the migration script runs, then for every character and every attribute/skill with a nonzero persisted `bonus`, an `st_mod` is created (`stat_path = attributes.<Attr>.bonus` / `skills.<Skill>.bonus`, `delta = the bonus value`, `reason = "Migrated legacy situational bonus"`, author = a system/service identity, `show_reason_to_player = false`) with a corresponding `created` audit event.
2. Given each successfully migrated bonus, when the st_mod is confirmed written, then the source `c.attributes[X].bonus` / `c.skills[X].bonus` is set to `0` on the character document.
3. Given the migration completes, when a character sheet renders, then the effective attribute/skill total is unchanged from before migration (the value moved from persisted base into the overlay; net display is identical).
4. Given the script runs, then it is idempotent and re-run-safe: a second run creates no duplicate mods (it detects that a matching migration mod already exists, or that `.bonus` is already zero) and reports zero new writes.
5. Given the migration, then an explicit before/after verification is produced: a pre-run count + dump of all nonzero `.bonus` values, and a post-run confirmation that (a) matching st_mods exist and (b) no nonzero persisted `.bonus` remains. The verification is committed as an artifact/log.

## Dev Notes

### Dependency & sequencing

- **Depends on 1034.1 (STM-14 feature)** merging and smoke-passing first. If the migration runs while the old `+○` controls still write `.bonus`, newly-typed bonuses would re-contaminate the field after migration. Order: 1034.1 → verify no UI writes `.bonus` → 1034.2 migration.

### Why this is safe (spike evidence, #1034)

Every nonzero persisted `.bonus` is, by construction, an ad-hoc manual ST bonus — the rules engine never writes `.bonus` (grants are read-time sums via `discAttrBonus`/`skTotal`, `accessors.js:38-48/109-114`). So converting all of them to st_mods loses no rule-granted data. Nothing reads `.bonus` expecting rule grants.

### Data shape to write (match the route exactly)

- st_mod doc (`server/routes/st_mods.js:133-144`): `{ character_id, stat_path, delta, reason, show_reason_to_player:false, active:true, created_by:{discord_id,discord_name}, created_at }`. Use a clearly-marked system `created_by` (e.g. discord_name `"system:migration"`).
- audit event (`buildAuditEvent`, `:96-107`): `{ st_mod_id, character_id, stat_path, delta, reason, event:'created', by, at }`. `by`/`at` mandatory (ADR-004 §D17).
- stat_path must pass the whitelist (`st_mods.js:39-40`): `attributes.<Attr>.bonus` / `skills.<Skill>.bonus`.

### Overlay correctness after migration

Once `.bonus = 0` and an st_mod carries the delta, the boot path `applyOverlayToAll` (`st-mods.js:196`) reapplies it at render (when the global overlay is enabled and the char is not `st_mods_suppressed`). Net effect: display unchanged (AC 3). Note the caveat: if the global overlay kill-switch is OFF or a character is `st_mods_suppressed`, the migrated bonus will not display (whereas the old persisted `.bonus` always displayed). Flag this in the PR — confirm the global overlay is enabled in prod before/after, or accept it as intended (suppression now hides ad-hoc bonuses too).

### Footguns (from memory/feedback)

- server/scripts dotenv-path trap: `import 'dotenv/config'` before `db.js`.
- No `find`+projection+`replaceOne` round-trips — use targeted `$set` to zero the one field (PR #813 destroyed 13 docs this way).
- Data-mutating script needs a ≥1 end-to-end test through `main()` (not helper mocks).

### Relevant source tree

- `server/routes/st_mods.js` — mod doc shape (`:133-144`), audit shape (`:96-107`), whitelist (`:39-40`)
- `public/js/data/st-mods.js` — `applyOverlayToAll` (`:196`), `applyStMods` (`:127`)
- `server/schemas/character.schema.js:358-361, 375` — `.bonus` field definition
- `server/scripts/` — existing script patterns (dotenv + db.js); backups dir for safety dumps

### Testing

- No app-wide test framework, but this data-mutating script REQUIRES an end-to-end `main()` test per project discipline (#813). Place under `specs/stories/tests/` or `server/scripts/` alongside the script; run with `node`.
- Manual/prod verification: read-only auditor before, migration (dry-run then live), auditor after (expect zero nonzero `.bonus`), sheet-total spot-check on 2-3 characters.
