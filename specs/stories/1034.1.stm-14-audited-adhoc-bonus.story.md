# Story 1034.1 (STM-14): Audited ad-hoc situational bonuses — retire the +○ editor control, apply via st_mods

## Status

Review

## Story

**As a** storyteller,
**I want** applying an ad-hoc situational bonus to a character's attribute or skill to go through the audited ST-mods channel (capturing reason, author, and timestamp) and to be toggleable,
**so that** every ad-hoc adjustment is accountable and the frictionless path is the auditable one, so the unaudited direct-edit workaround stops being used.

## Acceptance Criteria

1. Given an ST viewing a rendered character sheet, when they apply an ad-hoc situational bonus to an attribute or skill, then they are prompted for a reason and an audited `st_mod` is created (via `POST /api/st_mods`) targeting `attributes.<Attr>.bonus` or `skills.<Skill>.bonus`, with author + timestamp captured server-side and reason required.
2. Given a persisted character document, when an ST applies an ad-hoc bonus through this path, then `c.attributes[X].bonus` / `c.skills[X].bonus` on the character document is NOT written (the delta lives only in the st_mods overlay, per ADR-004 write-direction invariant §D6).
3. Given a character with active ad-hoc bonus mods, when the sheet renders, then the existing st-mod overlay applies the delta and the existing overlay marker/popover (`st-mod-popover.js`) shows base / adjustment / final with the reason (subject to `show_reason_to_player`).
4. Given an active bonus mod, when the ST toggles it inactive via the existing st-mods panel/lifecycle (STM-10), then the overlay recomputes without it and the toggle is recorded as an audit event; no hard delete required to remove the effect.
5. Given the editor (edit mode), when an ST enters it, then the old manual `+○ / −○` bonus controls (`adjAttrBonus`/`adjSkillBonus`/`shAdjAttrBonus`/`shAdjSkillBonus`) no longer write `c.attributes[X].bonus` directly — they are removed or repointed so no unaudited write path to the persisted `.bonus` field remains from the UI.
6. Overlay composition still runs solely through `applyStMods` (ADR-004 §D1/§D8); no second composition site is introduced; the overlay is still stripped on edit-mode entry (§D9).
7. Styling reuses existing STM component classes (`.stm-modal*` for the reason prompt, `.stm-mod-row`/`.stm-mod-btn` for lists, `.stm-ev-badge`/`.stm-marker` for chips/markers) and design-system tokens — no inline `style=`, no bare hex/`rgba()`.

## Dev Notes

### Why the apply affordance moves to the rendered sheet (not the editor)

ADR-004 §D8/§D9: the editor is the ONLY consumer that sees base values — the overlay is stripped on edit-mode entry (`stripOverlay`) and re-applied on save. The old `+○` control lives in the editor (`attrs-tab.js`), so if it created an st_mod the delta would be invisible while editing (overlay stripped) — confusing UX. Therefore the audited apply affordance belongs on the **rendered ST sheet**, where `applyStMods` has run and the st-mod marker/popover already exists. This is forced by the architecture, not a preference.

### Evidence base (spike, issue #1034)

- The rules engine NEVER writes `c.attributes[X].bonus` / `c.skills[X].bonus`. Merit/title/discipline grants are summed at READ time: `discAttrBonus` inside `getAttrEffective` (`public/js/data/accessors.js:38-48, 77-79`); PT/MCI skill grants via ephemeral Sets `c._pt_dot4_bonus_skills` / `c._mci_dot3_skills` summed in `skTotal` (`accessors.js:109-114`). All `_`-prefixed and transient.
- Therefore every NONZERO PERSISTED `.bonus` today is, by construction, an ad-hoc manual ST bonus. There is no rule-granted contamination to distinguish. (This is why redirecting the manual handlers is safe.)
- `.bonus` is a real persisted schema field (`server/schemas/character.schema.js:358-361` attrs, `:375` skills), sent through PUT (`buildSaveBody` admin.js; NOT in `_DEPRECATED_FIELDS`). Only transient `.bonus` writes are the st_mod overlay itself (`applyStMods` → `setByPath`, `st-mods.js:127-177`), which is snapshotted (`_st_mod_base`) and stripped before save.
- The audited overlay ALREADY whitelists these exact paths: `server/routes/st_mods.js:39-40` accepts `attributes.X.bonus` / `skills.X.bonus`; labels in `public/js/data/st-mod-labels.js`.

### st_mods create contract (reference: st-mods-panel.js:392-442)

```js
markLocalWrite(String(c._id), { st_mod: true });   // BEFORE the POST (WS-echo suppression)
await apiPost('/api/st_mods', {
  character_id: String(c._id),
  stat_path,                    // 'attributes.Strength.bonus' | 'skills.Brawl.bonus'
  delta,                        // non-zero integer
  reason,                       // required, trimmed, non-empty (server 400s if empty)
  show_reason_to_player: bool,
});
```
Server: `POST /api/st_mods` is `requireRole('st')` (`st_mods.js:113`); validates integer non-zero delta, non-empty reason, whitelisted stat_path; writes the mod + a `created` audit event with server-stamped `by`/`at` (never trust client for author/timestamp — ADR-004 §D17). WS broadcast `broadcastStModUpdate(id,'create',modId)`.

### Overlay application (read side, unchanged by this story)

`applyStMods(c, mods, overlayEnabled)` (`public/js/data/st-mods.js:127`) groups mods by `stat_path` (skipping `active===false`, line 141), strips prior overlay to avoid compounding, then `setByPath(c, path, base+delta)` and builds `c._st_mod_overlay[path] = {base, delta, final, mods}`. Boot path `applyOverlayToAll` (`st-mods.js:196`) is already wired at `app.js:637` / `admin.js:1328`. Do not add a parallel path (cache-entry invariant, ADR-004 §D8 / CLAUDE.md STM-7 note).

### ADR-004 invariants this story MUST respect

- §D6 write-direction: overlay is a read-direction display layer; never mutate `tracker_state` or the characters collection from the overlay path.
- §D8/§D9: single composition site; overlay stripped on edit-mode entry; `_`-prefixed fields stripped before PUT.
- §D15/§D16/§D17: lifecycle `active` boolean; append-only immutable `st_mod_audit`; `by`/`at` server-stamped and mandatory, per-toggle reason optional.
- Adding a second composition path or moving computation server-side requires a new ADR — out of scope here.

### Out of scope (this story)

- Migrating the existing persisted `.bonus` values — that is story **1034.2 (STM-14b)**, a prod-write with its own verification discipline.
- The prereq-override feature — that is **STM-15 (#1035)**, which builds on this.
- The two latent double-count roll bugs found in the spike (`public/js/game/char-pools.js:86` and `public/js/game/contested-roll.js:36-37` do `getAttrEffective(...) + getAttrBonus(...)`, double-adding `.bonus`) — file separately; do not fix here.
